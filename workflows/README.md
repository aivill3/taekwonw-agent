# workflows — 조합

에이전트를 순서대로 부르고 결과를 넘긴다. **판단 로직을 두지 않는다.**
`if`/`for` 와 예외 처리, 로깅까지가 여기 허용되는 전부다.

"이 기사를 쓸까?"를 여기서 결정하고 있다면 그 판단은 에이전트로 내려가야 한다.

| 파일 | 단계 | 사람의 개입 |
|---|---|---|
| `collect_workflow.py` | 수집 → 정제 → Notion(수집됨) → 랭킹 → **소주제 (LLM #1)** | 이후 '승인' 체크 |
| `subtopic_workflow.py` | '선정요청' 건만 소주제 생성 (LLM #1) | 이후 '승인' 체크 |
| `publish_workflow.py` | 초안 생성 (LLM #2) → 품질 측정 → 삽화 → Notion | — |

## collect 가 LLM을 부른다

`collect_workflow` 8단계가 소주제 생성이다. 랭킹이 뽑은 상위 건은 사람 손을
거치지 않고 소주제까지 만들어 '선정됨'으로 올린다. 사람은 승인만 하면 된다.

`subtopic_workflow` 는 파이프라인의 다음 단계가 아니라 **보조 경로**다.
랭킹이 놓친 기사를 사람이 '선정요청'으로 바꿔두면 그것만 처리한다.
두 워크플로가 같은 `generate_all()` 을 부르고, 경로만 자동·수동으로 갈린다.

LLM을 부르지 않는 두 경우는 소주제가 비므로 '선정됨'이 아니라 '선정요청'으로
올린다. 빈 채로 '선정됨'이 되면 `publish` 가 집어가 빈 초안을 쓴다.

| 조건 | LLM | 승격 상태 |
|---|---|---|
| 기본 | 호출 | `선정됨` |
| `--dry-run` | 생략 | (승격 자체를 하지 않음) |
| `--no-subtopic` | 생략 | `선정요청` |

`--dry-run` 에서 LLM을 부르지 않는 이유: Notion에 쓰지도 않으면서 무료 티어
할당량만 태우게 된다. 드라이런을 몇 번 돌리면 그날 RPD가 사라진다.

## 수집과 발행이 분리된 이유

승인은 사람이 하는 비동기 작업이다. 수집과 같은 실행에 넣을 수 없다.

## 재작성 방지

Notion '상태' 속성으로 진행 단계를 표시한다.

```
수집됨 → 선정요청 → 선정됨 → 작성완료
```

조회 조건이 `승인=True AND 상태=선정됨` 이고, 작성 후 `작성완료` 로 바꾼다.
원고 저장은 성공했는데 상태 변경이 실패하면 다음 실행에서 중복 작성될 수 있어,
그 경우 경고를 남긴다.

## 품질 측정은 게이트가 아니다

`publish_workflow` 의 3.5단계는 **측정 전용**이다. 어떤 지표가 미달이어도 발행을
막지 않는다. 측정 코드에서 예외가 나도 `try/except` 로 감싸 파이프라인을
중단시키지 않는다.

게이트로 승격하려면 먼저 오탐률을 누적 측정해야 한다. 결과는
`data/quality/metrics.jsonl` 에 쌓인다.

## 스케줄링

GitHub Actions cron은 `collect` 와 `publish` 만 걸면 된다. `subtopic` 은 사람의
선정을 기다려야 하므로 수동 또는 별도 시각에 돌린다.
